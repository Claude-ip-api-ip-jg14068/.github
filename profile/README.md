<p>断线重连这件事，最怕两种极端：一种是把锅全甩给网络，每次掉线就手动重连；另一种是迷信「自动重连」，参数没调，重连成功了但会话已经废了。真正要决策的其实是三个独立问题——你遇到的到底是断线还是速度抖动，批量开通要不要走 API，以及该选共享池还是自营线路。这篇把三个问题拆成可以逐条勾选的清单，每一项都给出判断条件、验证手段和取舍代价，照着走能少走不少弯路。</p>

<h2>一、先分清「断线」和「忽快忽慢」</h2>
<p>这两个症状经常被混为一谈，但成因和处置完全不同。断线是连接彻底中断，表现为请求直接超时、代理进程报错、网页打不开；忽快忽慢是连接还在，只是延迟从 200 毫秒跳到 1500 毫秒再回来，表现为页面转圈很久才出来、对话回复断断续续。</p>
<p>分不清就会做错决策。断线该做的是重连策略和主备切换；抖动该做的是换线路或换计费档位。给断线配更大的带宽没用，给抖动加重连参数也没用——反而可能因为频繁重连把本来能用的会话彻底掐死。</p>
<p>最简单的分辨办法：连续 10 分钟每秒请求一次出口查询接口，把耗时记下来。出现明确失败（连接被重置、超时无响应）算断线；全程有响应但 P95 耗时超过均值三倍，算抖动。两类数据都存在，说明线路质量本身就不合格，直接换线比调参划算。</p>

<h2>二、问题归属：三条分支判断</h2>
<h3>分支一：只有单个账号异常</h3>
<p>如果同一线路下别的号都正常，只有一个号反复掉，问题多半在会话层而不是网络层。先查这个号是否在别处登录过（设备列表）、浏览器配置目录是否被复制过、cookie 是否被同步工具带到了另一台机器。这类「掉线」其实是会话被顶掉。</p>
<h3>分支二：同线路下全部异常</h3>
<p>同一条线路上所有账号同时掉，问题在出口。按顺序查：代理进程是否存活、本地到网关的连通性、出口 IP 是否变更、服务商侧是否有公告。四项里前两项自己就能查，后两项要问商家。若出口 IP 变了且地区也变了，那不只是断线，账号侧还会有额外影响。</p>
<h3>分支三：随机时间点集体掉</h3>
<p>如果是每天固定时段（常见于凌晨）掉，基本是上游重拨或限速策略；如果是不定时掉且伴随延迟尖峰，多半是共享池被其他用户占满带宽。前者靠避开时段和加自动重连解决，后者只能靠换到独享或自营线路。</p>

<h2>三、API 对接：五个动作必须逐个验</h2>
<p>「支持 API 对接批量开通」这句话水分很大。有的只是给了一个开通接口，查询、续费、释放全要人工。对接前把下面五个动作逐个跑一遍，跑不通就问清楚，别等上线后才发现只有一半能自动化。</p>
<p>第一是鉴权：token 有效期多久、能不能续、是否支持 IP 白名单。第二是开通：接口是否幂等，重复提交同一订单会不会开出两条线路——这条最容易踩坑，重试一次多花钱。第三是状态查询：能否按订单号或线路编号查当前出口 IP、地区、剩余时长。第四是释放与续费：提前释放是否退费、自动续费能否关闭。第五是限流与错误码：QPS 上限多少、超限返回什么、失败时能否区分「参数错」和「资源不足」。</p>
<p>另有两个容易被忽略的点：一是批量开通的并发上限，很多接口单账号只允许 5 到 10 个并发请求，开一百条线要排队；二是开通到可用的时延，宣传的「即时开通」实际可能是 30 秒到 3 分钟，脚本里要留轮询等待，不要用固定 sleep。</p>

<h2>四、共享还是自营：四个判断条件</h2>
<h3>条件一：并发峰值有多高</h3>
<p>共享池的价格优势建立在「别人不用的时候你用」上面。如果你的业务有明显高峰（比如早十点到晚八点都在跑任务），共享池在高峰期必然被挤，速度忽快忽慢就是这么来的。峰值并发超过 5 条且持续时间超过 4 小时，就该考虑独享或自营。</p>
<h3>条件二：能否接受出口变更</h3>
<p>共享池为了调度效率，出口变更更频繁。如果你的账号需要长期固定地区，变更就意味着额外验证。自营线路通常可以按账号固定出口，代价是灵活性下降、单价上升。</p>
<h3>条件三：故障时谁负责排查</h3>
<p>共享池出问题时，服务商往往只能回答「池子在调度中」。自营线路的责任边界清晰，能给出具体线路的链路说明。团队里没有专职运维的，这一条权重应该调高——排查时间就是成本。</p>
<h3>条件四：预算与用量的匹配度</h3>
<p>月用量很小（比如每月几十 GB）时，自营的固定成本摊不下来。用量稳定且大，自营的单价优势才体现。建议先按「月流量 × 单价」和「固定月费」两个口径算一遍，再决定，不要只看单价。</p>

<h3>重试间隔与上限</h3>
<p>常见的错误是设成 1 秒重试、无限次。线路真断了，高频重试只会让本地连接表堆积，恢复后反而更慢。建议指数退避：1 秒、2 秒、4 秒、8 秒，上限 30 秒，总重试时长控制在 3 到 5 分钟，超过就切备用线路并告警。</p>
<h3>会话保活与心跳</h3>
<p>长连接场景下，把心跳间隔设在 30 到 60 秒比较稳妥，太短会增加无效流量，太长则线路静默断开后要等很久才发现。同时开启 TCP keepalive，让操作系统帮忙探测死连接，比应用层单打独斗可靠。</p>
<p>重连成功后第一件事不是继续发请求，而是核验出口 IP 和地区是否与断线前一致。不一致就按新环境处理，必要时重新登录，别在不知情的情况下继续操作。</p>

<h2>常见问答</h2>
<h3>自动重连成功后，原来的会话还能恢复吗？</h3>
<p>答：看会话绑定方式。绑定设备标识的通常能续上；绑定出口 IP 的，IP 一变会话就失效。判断方法是看断线前后出口 IP 是否相同，相同大概率能续，不同就要准备重新登录。</p>
<h3>API 开通的线路和后台手动开的有什么区别？</h3>
<p>答：多数情况下来源相同，区别在调度策略和优先级。部分服务商给 API 渠道单独的资源池，质量未必更好，要自己测。开通后仍建议按 ASN 归属、延迟抖动两条做一次抽检。</p>
<h3>共享池在夜间速度反而更快，正常吗？</h3>
<p>答：正常。共享池的瓶颈是并发占用，夜间其他用户退出后带宽释放，速度自然回升。这恰好说明你的瓶颈是共享而非线路本身，白天高峰期的表现才是决策依据。</p>
<h3>一条线路反复断，是不是该立刻换商家？</h3>
<p>答：先排除本地因素。代理进程崩溃、网卡节能、路由表异常都会伪装成线路故障。连续三天在同一时段复现、且换设备后仍复现，才基本可以归因到线路，这时候谈更换才有依据。</p>
